```
node (0x20 B):  +0x00 left   +0x08 right   +0x10 parent   +0x18 colour (1 = black)   +0x19 nil
tree (0x18 B):  +0x00 unread  +0x08 header  +0x10 count
```

The erase is `_Rb_tree_rebalance_for_erase` with explicit nil sentinels: the transplant prologue at
`0x482ab7..0x482c23`, the four rebalance cases at `0x482c27..0x482f04`, the count decrement, then
release through `0x170b0`. A nil argument is rejected by loading `"invalid map/set<T> iterator"`
(`0xffb153`) and calling `0xf8fc20`. `rb_next` before unlinking yields the returned successor.

**The reachability fact, stated rather than hidden.** `0x482960` opens with

```
49 8b 5d 00    movq 0x0(%r13), %rbx
49 3b 5d 00    cmpq 0x0(%r13), %rbx
0f 84 a6 00 00 00  je 0x482a3b
```

Both operands are the same load, so the comparison is always equal and the branch is always taken;
the loop at `0x4829b0..0x482a28`, which contains the **only** call site of `0x482a90` (`0x482a28`),
is unreachable in this image. llvm-objdump and rizin agree on both instructions. The taken path calls
`0x483240` on the root, resets the three header links and zeroes the count. Accordingly:

- `rb_clear_482960` models the taken path (post-order release + reset);
- `rb_erase_all_loop` models the loop the dead branch contains, so the erase is exercised;
- `rb_erase_482a90` is pinned and tested on its own as first-class code.

`0x483240`'s recursion edge is `+0x10` and its iteration edge is `+0x00`; combined with the erase's
`+0x10 = parent`, that is not a plain left/right post-order, so the destroy walk is modelled as the
equivalent post-order release and labelled INFERENCE wherever it cannot be observed. Slot 454's
three trees are empty at construction, so the walk is never entered by this slot.

## Traps found and repaired

- **Type collisions.** `RbNode`, `RbTree` and `RbHooks` already exist in the RB registry module; the
  first build caught the redefinitions. Renamed to `RbEraseNode` / `RbEraseTree` / `RbEraseHooks`.
- **Byte fields do not advance to their named offsets.** `zero6c`, `zero70`, `zero74`, `zero78` packed
  into adjacent bytes and the static assert failed at 200 B instead of 216. Fixed with explicit
  inter-byte gaps; the struct now asserts `0xd8`.
- **The fixture was wrong, not the erase.** Its "in-order" check pushed keys after both recursions
  (post-order), so a valid `1 < 3` tree failed `is_sorted`. The tree dump added to localize it showed
  the tree was correct; the push was moved between the recursions. This was a fixture bug and is
  recorded as such.
- **`--tamper-native` was fail-open.** The header names `SServerObjectProperties` twice (body comment
  and length pin); replacing one occurrence left the other and the checker still passed. It now
  mutates every occurrence and exits 1 with `FAIL native string b'SServerObjectProperties'`.
- **`source_order` had to be the real order**: `rb_tree_init` appears in the helper defined before
  `family_view`; the checker now lists that order instead of the call order inside `init_slot454`.
- The first draft of the RB checker carried two inert placeholder expressions that checked nothing;
  they were removed before the checker was accepted, so every line that remains pins bytes.
