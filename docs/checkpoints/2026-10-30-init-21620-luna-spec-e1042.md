## Finding

`0x21620` is a registry/map lookup, not the flat table scan implemented by
`lookup_1fc80`. It accepts a pointer to a key descriptor: the body dereferences
the first qword as a name pointer, and a secondary path also reads the qword at
`+0x08` and compares it with a registry node field. Do not treat the argument
as a raw `const char*` or assume the second field's meaning.

The pinned static disassembly shows a primary root path through a linked/tree
structure, comparing node names at `+0x20` via `0xf8f500` and returning the
matched node's value at `+0x40`. A separate path is taken when the primary root
is absent; it initializes/reads another static collection and compares both
name and the descriptor's second qword. It has calls to `0x3b390` and
`0x3b3c0` around the primary structure. Their exact lock contract and the
fallback initialization/ownership semantics remain unresolved.

## Comparison with existing code

- `lookup_1fc80` (`native/core/lookup_1fc80.hpp:1-31`) walks a `[begin,end)`
  array in `0x98`-byte strides and reads the name pointer at element `+0x28`;
  it returns the matching element. It has no tree traversal, secondary key,
  or synchronization contract. Reusing it for `0x21620` would be incorrect.
- The vslot miss hook (`native/core/vslot_40_533100_miss.hpp:33-36`) currently
  receives a synthetic stack hashed-string object whose full layout is not
  modelled. `lazy_bind_91210` (`native/core/lazy_bind_91210.hpp:27-35`)
  receives `this+8`, a key-slot pointer, through a host-bearing callback.
  Both callsites pass an address of a key-like descriptor to `0x21620`, but
  equivalence of the complete descriptor (especially `+0x08`) is not yet
  established.
- Caller pins: `0x91210` calls `0x21620` at `0x91227` with `rdi=this+8`; the
  E530 checkpoint identifies the associated name as `shadowDemoMode`. The
  vslot miss calls it at `0x53327d` after constructing the stack key for
  `r_fps` (existing checker `tools/lift/check_f533100_vslot40_miss.py`). The
  callee's reads at key `+0x00` and, on its fallback path, `+0x08` make the
  existing vslot stand-in's first-qword-only treatment insufficient as proof
  that the two keys have the same full layout.
- Recommendation: one shared `lookup_21620` core, plus two thin typed
  adapters for the current vslot and lazy-bind hook signatures. The adapters
  should forward the same opaque key descriptor and their host context. Do not
  wire either adapter to native lookup until both descriptor layouts are
  byte-checked against the callee's reads.

## Stop rules

Do not implement or wire native lookup if any of these remain unresolved:

1. The 0x08-byte key descriptor contract cannot be verified at **both** call
   sites, including the meaning and validity of its second qword.
2. The primary registry's root/node layout or the second fallback collection's
   boundaries and initialization effects cannot be represented without
   guessing.
3. `0x3b390` / `0x3b3c0` lock lifetime, comparator ordering/equality, or result
   ownership/lifetime is unknown.
4. The implementation would need to invent a `shadowDemoMode` result or treat
   a fixture hit as proof of a live engine bind.
5. A checker only pins 449 bytes and omits the reachable cold block/tail.

Keep `0x21620` as a fail-closed hook until these contracts are pinned. No
boot/audio/save/Metal or `engine_ready` claim follows from this lookup work.
